# Project and Notebook Files System — Historical Proposal (Name-Based Storage)

This document is retained as the original proposal for the name-based storage migration. The live reference architecture is now `docs/project-and-notebook-files-system.md`; use that document for current behavior. This proposal remains useful for understanding the migration intent and design tradeoffs.

---

## 1. Overview: Name-Based File Tree

The platform maintains a file tree under a configurable storage root where project and notebook directories use human-readable names (sanitized slugs) instead of GUIDs. Notebooks are physically subordinate to their project directory.

Two file domains remain logically distinct:

- **Project Files** — versioned, library-managed files. Organized in explicit folder hierarchies visible through the UI. Internal storage structures (versioned file blobs, content-addressable storage, markdown shadows) retain their existing directory layout but with slugs replacing GUIDs in path segments.
- **Notebook Files** — filesystem-first files in named subdirectories of the project. The filesystem is the source of truth; the database mirror is maintained via sync.

The internal directory structure (`files/`, `projects/.../content/`, `projects/.../markdown/`) was intended to be preserved from the former GUID-based architecture. The change was strictly: GUIDs become slugs, and the `notebooks/` intermediate segment is removed.

## 2. Physical Storage Layout

### 2.1 Directory Tree

Given a storage root of `/data/guideants` (or `D:\GuideAnts\Projects` on Windows):

```
{storage}/
├── my-research-project/                 ← project slug (was a GUID)
│   ├── files/                           ← versioned project file storage (unchanged structure)
│   │   └── {fileGuid}/v{n}/{fileName}
│   ├── analysis-notebook/               ← notebook slug (direct child, was under notebooks/{guid})
│   │   ├── Output/                      ← private tool/script output directory
│   │   ├── Resources/                   ← guide crew files, modules
│   │   ├── data/
│   │   │   └── dataset.csv
│   │   └── report.md
│   └── exploration-notebook/            ← another notebook
│       └── ...
├── projects/
│   └── my-research-project/             ← slug replaces GUID in existing structure
│       ├── content/                     ← content-addressable blobs (unchanged structure)
│       │   └── {aa}/{bb}/{hash}
│       ├── analysis-notebook/           ← slug replaces notebooks/{guid} segment
│       │   └── markdown/               ← notebook markdown shadows (unchanged structure)
│       │       └── {aa}/{bb}/{hash}.md
│       └── content/                     ← project markdown shadows share this tree
│           └── {aa}/{bb}/{hash}.md
└── another-project/
    └── ...
```

### 2.2 Key Layout Changes from the Former GUID-Based Architecture

| Aspect | Former GUID-based baseline | Proposed name-based layout |
|--------|----------------------|----------------------|
| Project root | `{storage}/{projectGuid}/` | `{storage}/{projectSlug}/` |
| Notebook root | `{storage}/{projectGuid}/notebooks/{notebookGuid}/` | `{storage}/{projectSlug}/{notebookSlug}/` |
| Intermediate `notebooks/` segment | Present | Eliminated |
| Versioned project files | `{storage}/{projectGuid}/files/{fileGuid}/v{n}/...` | `{storage}/{projectSlug}/files/{fileGuid}/v{n}/...` |
| Content-addressable blobs | `{storage}/projects/{projectGuid}/content/...` | `{storage}/projects/{projectSlug}/content/...` |
| Notebook markdown shadows | `{storage}/projects/{projectGuid}/notebooks/{notebookGuid}/markdown/...` | `{storage}/projects/{projectSlug}/{notebookSlug}/markdown/...` |
| Project markdown shadows | `{storage}/projects/{projectGuid}/content/{aa}/{bb}/{hash}.md` | `{storage}/projects/{projectSlug}/content/{aa}/{bb}/{hash}.md` |
| Container mount | `/app/ContentFiles/{projectGuid}/notebooks/{notebookGuid}/...` | `/app/ContentFiles/{projectSlug}/{notebookSlug}/...` |
| User visibility | Opaque (users never see storage) | Project and notebook directories are browsable |

### 2.3 Container Mount Convention

Host bind mount remains `./volumes/content-files:/app/ContentFiles` (configurable). Container paths become:

- Working directory (private): `/app/ContentFiles/{projectSlug}/{notebookSlug}/Output`
- Working directory (published run): `/app/ContentFiles/{projectSlug}/{notebookSlug}/Runs/{runId}`
- Notebook root: `/app/ContentFiles/{projectSlug}/{notebookSlug}`

## 3. Core Entities

### 3.1 Project

Unchanged semantics. Adds a `Slug` property: a sanitized, filesystem-safe, lowercase, unique identifier derived from the title. The slug is used as the project's directory name.

- `Slug` — required, unique, max 100 characters, generated by `SlugGenerator` from `Title`
- `Title` — display name, may contain any Unicode characters, max 255 characters (unchanged)
- All other properties unchanged

Server model: `src/server/GuideAntsApi.DataModel/Models/Project.cs`

### 3.2 Notebook

Unchanged semantics. Adds a `Slug` property: sanitized, filesystem-safe, lowercase, unique within the project. The slug is used as the notebook's directory name, placed directly inside the project directory (no intermediate `notebooks/` segment).

- `Slug` — required, unique per `(ProjectId, Slug)`, max 100 characters
- `Title` — display name (unchanged)
- All other properties unchanged

Server model: `src/server/GuideAntsApi.DataModel/Models/Notebook.cs`

### 3.3 ContentFile (Project File)

`Path` field semantics change: instead of storing `{storage}/{projectGuid}/files/{fileGuid}`, it stores `{storage}/{projectSlug}/files/{fileGuid}`. The `RelativePath` (logical path within the project) and `FileName` remain unchanged.

`GenerateDocumentId()` changes to hash `{ProjectId}:{RelativePath}` instead of `Path`, making the DocumentId stable across project renames.

Physical storage: `{storage}/{projectSlug}/files/{fileGuid}/v{n}/{fileName}` for versioned files (structure unchanged, GUID segment replaced with slug).

Server model: `src/server/GuideAntsApi.DataModel/Models/ContentFile.cs`

### 3.4 ContentFileVersion

`StoragePath` stores the content-addressable path: `{storage}/projects/{projectSlug}/content/{aa}/{bb}/{hash}` (structure unchanged, GUID replaced with slug).

Legacy `Path` field stores the versioned path: `{storage}/{projectSlug}/files/{fileGuid}/v{n}/{fileName}`.

All lineage fields (`OriginNotebookFileId`, `FromNotebook`, etc.) remain unchanged — they reference entity GUIDs, not paths.

Server model: `src/server/GuideAntsApi.DataModel/Models/ContentFileVersion.cs`

### 3.5 ProjectFolder

`GetPhysicalPath()` changes to use `PathResolver` instead of `Path.Combine(basePath, ProjectId.ToString(), RelativePath)`. Logical `RelativePath` within the project remains unchanged.

Server model: `src/server/GuideAntsApi.DataModel/Models/ProjectFolder.cs`

### 3.6 NotebookFile

No structural changes. `RelativePath` remains relative to the notebook root. `GenerateDocumentId()` continues to use `{NotebookId}:{RelativePath}` — stable because it uses the GUID.

Physical location changes from `{storage}/{projectGuid}/notebooks/{notebookGuid}/{relativePath}` to `{storage}/{projectSlug}/{notebookSlug}/{relativePath}`.

Server model: `src/server/GuideAntsApi.DataModel/Models/NotebookFile.cs`

### 3.7 AssistantFile

Unchanged. Assistant files use their own storage path convention under `assistants/` which is not affected by this migration.

Server model: `src/server/GuideAntsApi.DataModel/Models/AssistantFile.cs`

## 4. Slug System

### 4.1 SlugGenerator

A new utility class that converts titles to filesystem-safe slugs:

1. Lowercases the input
2. Replaces spaces with hyphens
3. Removes characters invalid for filesystems on both Windows and Linux
4. Collapses consecutive hyphens
5. Trims leading and trailing hyphens
6. Rejects Windows reserved device names (CON, PRN, AUX, NUL, COM1-9, LPT1-9)
7. Truncates to maximum slug length (100 characters)
8. Appends a numeric suffix if the slug collides with an existing one in the same scope

Location: `src/server/GuideAntsApi/Services/SlugGenerator.cs`

### 4.2 Uniqueness Constraints

- `Project.Slug` — unique index (case-insensitive)
- `(Notebook.ProjectId, Notebook.Slug)` — unique composite index (case-insensitive)

Enforced at both the database and API validation layers.

## 5. PathResolver Service

A centralized service that encapsulates all filesystem path construction, replacing the 40+ inline `Path.Combine` / string interpolation sites across the codebase.

### 5.1 Responsibilities

- Resolve project root: `{storage}/{projectSlug}`
- Resolve notebook root: `{storage}/{projectSlug}/{notebookSlug}`
- Resolve content-addressable path: `{storage}/projects/{projectSlug}/content/{aa}/{bb}/{hash}`
- Resolve versioned file path: `{storage}/{projectSlug}/files/{fileGuid}/v{n}/{fileName}`
- Resolve notebook working directory (host): `{storage}/{projectSlug}/{notebookSlug}/Output` or `Runs/{runId}`
- Resolve notebook working directory (container): `/app/ContentFiles/{projectSlug}/{notebookSlug}/Output` or `Runs/{runId}`
- Resolve markdown shadow paths for both project and notebook scopes
- Cache GUID-to-slug mappings with invalidation on rename

### 5.2 Interface

The service accepts entity GUIDs as input and resolves the corresponding slug from its cache (or database). This means callers do not need to know or pass slugs — the resolver handles the translation internally.

Location: `src/server/GuideAntsApi/Services/PathResolver.cs`

## 10. Database Layer

### 10.1 Schema Changes

New columns:
- `Project.Slug` — `nvarchar(100)`, required, with unique index
- `Notebook.Slug` — `nvarchar(100)`, required, with unique composite index on `(ProjectId, Slug)`

New indexes:
- `IX_Projects_Slug` — unique
- `IX_Notebooks_ProjectId_Slug` — unique composite

`ContentFile.GenerateDocumentId()` logic change: hash input switches from `Path` to `{ProjectId}:{RelativePath}`.

### 10.2 Data Migration

A one-time migration:
1. Generates slugs for all existing projects and notebooks
2. Resolves collisions with numeric suffixes
3. Populates the new `Slug` columns
4. Regenerates `ContentFile.DocumentId` values using the new formula
5. Updates `DocumentChunk.DocumentId` references to match

## 12. API Endpoints

- `/api/projects/{projectId:guid}/...`
- `/api/projects/{projectId:guid}/notebooks/{notebookId:guid}/...`

All endpoints that resolve filesystem paths (file content, upload, download, lineage) internally switch from inline GUID-based path construction to `PathResolver`. No external API signature changes.

## 14. Cross-Domain Operations: Copy and Publish

### 14.1 Copy from Project to Notebook

Unchanged semantics. Physical paths resolved via `PathResolver`: source from project's versioned `files/` or content-addressable storage, destination to notebook's named directory.

Unchanged semantics. Source resolved from `{projectSlug}/{notebookSlug}/{relativePath}`, destination written to `{projectSlug}/files/...` and `projects/{projectSlug}/content/...`.

## 17. Data Flow Diagrams (Logical)

### 17.1 Notebook File Lifecycle (Updated)

1. Files arrive in the notebook directory (`{projectSlug}/{notebookSlug}/...`) via upload API, tool output, or copy-from-project.
2. `NotebookFileSyncService` reconciles disk state with `NotebookFile` database records (unchanged logic, new path resolution via `PathResolver`).
3. Extraction, transcription, and indexing pipelines unchanged — handlers use `PathResolver` for path construction.
4. Markdown shadows stored in `projects/{projectSlug}/{notebookSlug}/markdown/...`.

### 17.2 Project File Lifecycle (Updated)

1. Files uploaded via API.
2. Versioned copies stored in `{projectSlug}/files/{fileGuid}/v{n}/...`.
3. Content-addressable blobs in `projects/{projectSlug}/content/...`.
4. Extraction and indexing pipelines unchanged.

### 17.3 Rename Flow (New)

1. User renames project or notebook via UI.
2. `SlugGenerator` produces new slug from new title.
3. If slug changed, `PathResolver` cache is invalidated.
4. Physical directory renamed via `Directory.Move`.
5. Affected `StoragePath` columns updated in `ContentFileVersion`, `ContentFileMarkdownShadow`, `NotebookFileMarkdownShadow`.
6. `FileLineageEvent.StoragePath` is not updated (historical audit).
7. `DocumentId` values are unaffected (GUID-based generation).

## 18. Entity Relationship Summary

Unchanged from the former architecture. All relationships use GUID foreign keys, not paths:

- **Project** → many `ContentFile`, `ProjectFolder`, `Notebook`; optional `HomePageContentFile`
- **ProjectFolder** → self-referencing parent/child; many `ContentFile`
- **ContentFile** → many `ContentFileVersion`; optional `ProjectFolder`; many `DocumentChunk`
- **ContentFileVersion** → optional `ContentFileMarkdownShadow`; optional `OriginVersion`; optional `OriginNotebookFile`
- **Notebook** → `Project`; optional `Guide`; many `NotebookConversation`, `NotebookFile`; optional `HomePageFile`, `HomePageConversation`
- **NotebookFile** → `Notebook`; optional `OriginContentFileVersion`; many `DocumentChunk`, `MessageAttachment`
- **NotebookFileMarkdownShadow** → `NotebookFile`
- **DocumentChunk** → exactly one of `ContentFile` | `NotebookFile` | `AssistantFile`
- **MessageAttachment** → `NotebookConversationMessage` + `NotebookFile`
- **FileLineageEvent** — standalone audit, references `FileId` and `FileKind`

New properties on existing entities:
- **Project** adds `Slug`
- **Notebook** adds `Slug`
