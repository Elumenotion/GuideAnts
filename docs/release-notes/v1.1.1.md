# GuideAnts v1.1.1 – Draft Release Notes

**Published-guide auth bypass closed, and the app no longer refuses to start over an AI sandbox route shape** – plus the Spark (DGX / GB10) backend is now published to GHCR and pulled by the launcher instead of built locally, and the installer works with zero optional components selected.

## What's new since v1.1.0

- **Published-guide auth bypass fixed** – The auth check for published guides was deciding the mode from the stored `AuthMode` column. That column is redundant with the actual credential columns and was the source of a bypass: a guide with a configured API key (or webhook URL) could be treated as anonymous, and `ValidateAsync` would return valid without ever checking the key. Auth is now **derived from the credential columns** via a new `PublishedGuideAuthService.EffectiveAuthMode()`: a non-empty `ApiKeyHash` always forces `ApiKey` validation, a non-empty `AuthValidationWebhookUrl` forces `Webhook`, `AppIdentity` is preserved for internal guides only, and only a guide with **no** credential is anonymous (precedence: API key > webhook > AppIdentity > anonymous). `AuthMode` is now kept in sync on publish/update, and the `requiresAuth` field in the published-guide DTOs and the wire-API execution-context resolver both use `EffectiveAuthMode`, so what the API advertises and what it enforces agree.
- **Startup no longer blocked by AI sandbox route shape** – A misconfigured `ServiceRouting:Containers:guideants-ai:BaseUrl` (missing the `/sandbox` prefix) used to throw at boot and prevent the whole app from starting. The startup path (`ServiceRoutingStartupValidator.Validate`) now treats that finding as **readiness-only** and skips it, so a bad AI route degrades to readiness / dispatch-time failures on the affected service instead of blocking startup. The readiness path (`Evaluate`) still reports it, so the Settings UI can surface the blocker.
- **Spark (DGX / GB10) backend published to GHCR** – The Spark AI image is now `ghcr.io/elumenotion/guideants-ai-spark:main`, pulled by `installer/guideants-spark.sh` and `docker-compose.spark.yml` (`pull_policy: missing`) rather than requiring a local `guideants-ai:spark` build (`pull_policy: never`). All support images are pulled from the registry: `docling` / `documentserver` from quay / GHCR, and `searxng` / `plantuml` (amd64-only on GHCR) pinned to `linux/amd64` and run under emulation.
- **Installer works with zero optional components** (#159) – The `Components` parameter on `Save-InstallerState`, `Invoke-InstallerStartStack`, and `Get-InstallerActiveServices` was `Mandatory`, so an install with no optional components selected failed. It now defaults to an empty array, and the pull loop `continue`s on a failed pull instead of aborting.
- **Digest-pulled images get a readable tag** (#159) – Images pulled by digest (`@…`) have no tag, so `docker images` showed `<none>`. The installer now best-effort tags them `repo:<channel>` (non-fatal) so they have a readable name in `docker images`.

## What's under the hood

- **Published-guide auth** – `PublishedGuideAuthService.EffectiveAuthMode(PublishedGuide)` (static, new source of truth); `ValidateAsync` dispatches on it; `AuthMode` maintained in `GuidesPublishingEndpoints` (create, update, key generate, key delete) and consumed in `PublishedGuidesEndpoints` (`requiresAuth`) and `PublishedApiExecutionContextResolver.ResolveAuthMode`.
- **Startup validator** – `ServiceRoutingStartupValidator.Evaluate` gains `includeReadinessOnly` (default `true`); `Validate` calls it with `includeReadinessOnly: false`; new `IsReadinessOnlyError` classifies the `guideants-ai:BaseUrl` finding. Test renamed `Validate_RejectsLegacyGuideantsScriptBaseUrl` → `Validate_AllowsLegacyGuideantsScriptBaseUrl_ReadinessOnly` and now asserts the startup path does not throw while readiness still reports the finding.
- **Spark sandbox requirements split** – New `docker/build/Sandboxes/python311TorchCUDA/requirements.spark.txt` (aarch64), derived from `requirements.txt` with the x86_64-only C-extension pins removed (no aarch64 wheel on PyPI; they fail source builds): `basemap`, `basemap-data`, `fiona`, `kerykeion`, `pyswisseph`, `rasterio`, `wordcloud`. Verified against PyPI wheel tags; `Dockerfile.cuda-spark` pins `setuptools<81`.
- **Spark build + pull model** – `build_guideants_ai.{ps1,sh}` cross-compile the `spark` backend for `linux/arm64` via buildx (QEMU on x86 hosts; native on the Spark). `--rebuild-base` now preserves the layer cache and re-pulls upstream (instead of `--no-cache`), so rebuilds are faster. `build_support_images.{ps1,sh}` build arm64 in `-Spark` mode.
- **Local (no-Docker) combined build** – New `src/server/build_local.ps1` and `npm run server:build:local`: builds the server + browser UI folder on the host without Docker, mirroring the docker `runtime-base` stage layout (`dotnet publish` → `<OutDir>`, bootstrap resources → `<OutDir>/Resources/bootstrap`, UI → `<OutDir>/ui`).

## Notes

- **Security – upgrade recommended** if you have any published guides with an API key or webhook configured. Before this release, the enforced auth mode could disagree with the configured credential; this release closes that. No data migration is required; the mode is re-derived from existing credential columns at request time.
- The Spark launcher now assumes GHCR access for `guideants-ai-spark` (`docker login ghcr.io`). It no longer builds the AI image.
