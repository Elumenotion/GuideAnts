# GuideAnts v1.1.2

**Spark (DGX / GB10) support images are now first-class, arch-isolated, and released alongside the AI images** – the push pipeline no longer clobbers `main`/`latest` when building for ARM64, and `-RebuildBase` preserves the layer cache.

## What's new since v1.1.1

- **Architecture-aware support image push** – `push-ghcr-guideants-ai.{ps1,sh}` now inspects each local support image's actual architecture before pushing. AMD64 images go to the shared mutable tags (`main`, `latest`, release tag); ARM64 images go to arch-suffixed tags (`main-arm64`, `latest-arm64`, `<release>-arm64`). A **hard guard** refuses to push an image under the other arch's tags – the class of defect where a Spark build silently overwrote `main` with an arm64 image (breaking all amd64 stacks) is now impossible by construction.

- **Spark support images tagged natively** – `build_support_images.{ps1,sh}` in `-Spark` mode now tags locally as `:arm64` (e.g. `plantuml-1.2025.2:arm64`, `guideants-searxng:arm64`) instead of overwriting `:latest`. Reuse hashes are mode-prefixed (`amd64:` / `arm64:`) so a cached hash from one mode can never satisfy the other mode's reuse check. The Spark compose (`docker-compose.spark.yml`) consumes `:main-arm64` tags natively – no `platform:` pin, no QEMU emulation.

- **AMD64 compose files pin `platform: linux/amd64`** – All five GHCR compose files (`ghcr-cuda13`, `ghcr-cpu`, `ghcr-rocm`, `ghcr-vulkan`, `ghcr-slim`) now pin `platform: linux/amd64` on the `plantuml` and `searxng` services. If a future arch clobber ever slips through, the pull **fails loudly** instead of silently running under emulation.

- **`-RebuildBase` preserves layer cache** – `build_guideants_ai.{ps1,sh}` previously passed `--no-cache` on `-RebuildBase`, discarding all layer cache (including the multi-minute C++ compiles for sd-cli and audiocpp_server). It now keeps `--cache-from` (local BuildKit cache + tagged deps image) and adds only `--pull` to re-check the upstream llama.cpp base. Only layers that actually changed rebuild.

- **Release tags cover both arches** – `-ReleaseTag v1.1.2` stamps both the amd64 support images (`v1.1.2`) and the arm64 support images (`v1.1.2-arm64`). The Spark AI image gets `v1.1.2` in its own repo (`guideants-ai-spark`), as before.

## What's under the hood

- **Push pipeline rework** – `Push-SupportImage` (PS1) / `push_support_image` (sh) replace the flat `extra_targets` array. Each support image declares its local repo name, remote package name, amd64 tag set, and arm64 tag set. `Get-ImageArch` / `get_image_arch` inspect the source image before any tag/push. The guard throws with the offending image ref, detected arch, and expected arch.
- **`Get-LocalBuildxCacheFromArgs`** is now always applied (was previously skipped under `-RebuildBase`); `--no-cache` is removed from both the deps and final build stages in both scripts.
- **`build_support_images` spark-mode tag split** – `$plantumlImageTag` / `$searxngImageTag` are computed from the mode at the top of each section; the build command uses the computed tag. Hash file writes are prefixed so the reuse check is mode-aware in both directions.
- **Spark compose** – `plantuml` and `searxng` image refs changed from `:main` + `platform: linux/amd64` to `:main-arm64` (no platform pin). Header comment updated.

## Notes

- **One-time migration for existing hosts** – If you ran `build_support_images.ps1 -Spark` before this release, your local `plantuml-1.2025.2:latest` and `guideants-searxng:latest` may be arm64. Run `build_support_images.ps1` (normal mode) to rebuild them as amd64. If you also ran a full `push-ghcr-guideants-ai.ps1` after that spark build, the GHCR `main`/`latest` tags for `guideants-plantuml` may be arm64 – re-run `publish-plantuml-image.yml` (CI) or a normal-mode push to restore.
- **MSSQL remains amd64-only** – `mssql2025-express-fts` has no arm64 build (Microsoft ships no arm64 `mssql/server` image). The Spark stack does not include MSSQL.
- **Multi-arch manifests are not used** – Each arch gets its own tag. This keeps the local `docker tag` + `docker push` path (no buildx multi-platform required at push time) and makes the arch boundary explicit in the tag name. A future multi-arch manifest under a single tag is compatible with this layout (the `-arm64` tags would simply become redundant).
